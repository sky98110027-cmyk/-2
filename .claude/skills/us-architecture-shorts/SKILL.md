# 영어권 건축 원리 3D 쇼츠

신기한 건축물·구조물의 작동 원리를 세로 영상으로 설명하는 **영어** 쇼츠를 만든다.
사람은 등장하지 않는다. 구조물이 스스로 조립되거나 움직이는 과정을 보여주고 나레이션이 원리를 설명한다.

일본판(`japan-architecture-shorts`)과 제작 골격은 같다. **다른 것은 세 가지다.**

1. 언어가 영어다. 음성 엔진이 VOICEVOX가 아니라 MCP 음성 도구다
2. 뒤집을 통념을 **영어권 대중 기준**으로 잡는다
3. 자막 한 줄 상한이 전각 14자가 아니라 **영문 28자**다

## 고정 사양 — 매번 다시 묻지 않는다

- 세로 9:16 / 1080×1920 / 30fps
- 송출 대상 영어권(미국 중심). 나레이션·자막 모두 영어
- 나레이션: MCP `generate_audio`, 기본 모델 **seed_audio**, 남성 해설 톤
- 이미지·영상: TopView AI MCP
- 조립: ffmpeg (`scripts/assemble.py`)
- 룩: 사실적 3D 건축 시각화 + 주황색 계측선

**새 영상에서 물어볼 것은 주제와 목소리 둘뿐이다.** 스타일 갤러리를 다시 열지 않는다.

**영상 길이는 고정이 아니다.** 대본을 목표 초수에 맞춰 늘리거나 줄이지 않는다.
실제 길이는 나레이션을 먼저 합성해 실측한 발화 길이의 합으로 결정한다.
결과가 20초든 40초든 그게 맞는 길이다.

## 작업 순서

컨펌 지점은 ■. 단 사용자가 "승인 없이 계속"이라고 하면 멈추지 않고 끝까지 간다.

### 0. 목소리 확인 ■

기본값은 seed_audio의 남성 해설 보이스. 그대로 가겠다고 하면 더 묻지 않는다.
대안은 `references/voice.md`의 선택 규칙대로 2~3개만 제시한다.

**목소리를 바꾸면 길이가 통째로 바뀐다.** 엔진·보이스마다 발화 속도가 다르다.
바꾸면 반드시 재합성·재실측하고 컷 수도 다시 나눈다.

### 1. 대본 작성

**먼저 상식을 뒤집을 지점을 찾는다.** 이 채널의 훅은 "신기하다"가 아니라 "네가 알던 게 틀렸다"다.

1. 영어권 대중이 그 구조물에 대해 믿고 있는 통념을 특정한다
2. 그 통념을 반박하는 실제 증거·최신 연구를 웹 검색으로 확인한다
3. 검증되지 않은 주장(외계인, 초고대문명 등)은 쓰지 않는다
4. 어떤 통념을 어떤 근거로 뒤집는지 한 줄로 명시하고 출처 URL을 `script.json`에 남긴다

**통념은 영어권 기준으로 잡는다.** 이게 일본판과 갈리는 가장 큰 지점이다.
일본판 스카이트리편을 영어로 번역하면 실패한다. 영어권 시청자는 오중탑도 심주도 모르기 때문에
뒤집을 통념 자체가 성립하지 않는다.

영어권에서 실제로 통하는 통념의 예:

- 후버댐 — "콘크리트가 아직도 굳고 있다"
- 엠파이어스테이트 — "번개를 피하려고 첨탑을 세웠다"
- 게이트웨이 아치 — "포물선이다"
- 골든게이트 — "케이블이 다리를 매달고 있다"
- 피사의 사탑 — "기울어진 채로 그냥 두고 있다"

선택한 통념이 영어권에서 실제로 퍼져 있는지 **웹 검색으로 확인한 뒤** 쓴다.
한국인이 아는 통념을 영어로 옮기지 않는다.

3블록 구성이 기본. 원리 설명에 더 필요하면 4블록까지 늘려도 된다.

- 블록 1 (훅) — 통념을 짧게 제시하고 곧바로 부정한다
- 블록 2 (원리) — 실제로는 어떻게 되어 있는지 구조·물리로 설명
- 블록 3 (반전 마무리) — 첫 문장의 통념을 다시 뒤집으며 닫는다

**블록당 두 문장까지.** 할 말이 끝났으면 거기서 끝낸다.
사용자가 대본을 직접 써서 줬다면 한 글자도 바꾸지 않는다.

영어 표기 규칙과 `script.json` 스키마는 `references/script-writing.md`를 읽는다.

### 2. 대본 확인 ■

대본 전문 + 뒤집는 지점 + 근거 출처를 제시하고 승인받는다.
수정 요청이 오면 대본만 고치고 다시 확인받는다. 승인 전에 이미지를 만들지 않는다.

### 3. 나레이션 합성 및 실측 — 길이 확정

**이미지보다 나레이션이 먼저다.** 음성은 싸고, 여기서 나온 숫자가 뒤의 모든 것을 결정한다.

줄을 **한 줄씩 따로** 합성한다. 통짜로 합성하면 줄별 시각을 알 수 없어 자막 정렬이 무너진다.
받은 파일을 `audio/001_*.wav`, `002_*.wav` … 순서대로 저장한 뒤 실측한다.

```
uv run scripts/measure_timing.py projects/<슬러그>
```

`measure_timing.py`는 엔진을 가리지 않는다. 줄별 WAV 길이만 읽는다.
합성 절차와 저장 규칙은 `references/voice.md`.

**대사를 길이에 맞춰 고치지 않는다.** speech_rate·atempo·무음 잘라내기 금지.
길이가 대사를 따라온다.

### 4. 스토리보드 작성

**컷당 2초 기준.** 블록 길이 ÷ 2 = 컷 수.

컷마다 적는다: 카메라 앵글 / 화면에 무엇이 있는지 / 무엇이 움직이는지 /
주황색 주석이 무엇을 가리키는지 / 대응하는 나레이션 구절.

앵글은 `references/visuals.md`의 팔레트에서 고르고 **연속된 컷에 같은 앵글을 반복하지 않는다.**
`storyboard.md`에 남기고, 여기서 멈추지 않고 5단계로 이어간다.

### 5. 이미지 생성 (TopView)

**스타일 키 → 에셋 시트 → 컷 이미지** 순으로, 앞 단계 결과물을 뒤 단계의 레퍼런스로 넘긴다.
컷을 텍스트만으로 생성하면 구조물 모양이 컷마다 달라진다.

스타일 포뮬러·네거티브·TopView 호출 규칙은 `references/visuals.md`. **한 글자도 바꾸지 않고** 붙여넣는다.

### 6. 이미지 컨펌 ■

생성된 이미지를 전부 보여주고 승인받는다. 재생성 요청이 오면 해당 컷만 다시 만든다.
승인 전에 영상 블록을 만들지 않는다. **영상이 이미지보다 훨씬 비싸다.**

### 7. 영상 제작 및 조립

이미지는 컷 단위지만 **영상은 블록 단위로 묶어 생성한다.** 비용 때문이다.
블록의 첫 컷 이미지를 `firstFrameFileId`로 넣고 프롬프트에 그 블록의 카메라 무브를 이어 쓴다.
블록 길이는 TopView 생성 가능 길이 중 실측을 덮는 가장 가까운 값으로 올려 잡고 끝을 잘라낸다.

```
uv run scripts/check_reading.py projects/<슬러그>
uv run scripts/build_ass.py projects/<슬러그>
uv run scripts/assemble.py projects/<슬러그>
```

자막·조립 세부는 `references/assembly.md`.

### 8. 최종 컨펌 ■

완성본을 전달하고 승인받는다.
수정 요청 시 어느 단계로 되돌아가야 하는지(대본/나레이션/이미지/영상)를 먼저 판단해 알리고 진행한다.

**업로드 시 사용자에게 반드시 상기시킨다** — 유튜브 스튜디오의
'변경되거나 합성된 콘텐츠(altered or synthetic content)' 공개 토글을 켤 것.
미공개는 경고 → 90일 수익 정지 → 영구 퇴출로 이어진다.

## 폴더 구조

```
projects/<슬러그>/
    script.json               대본·통념·출처·보이스 설정
    timing.json               줄별 실측 시각
    storyboard.md             컷별 앵글·화면·주석
    prompts.json              스타일 키·에셋 시트·컷별 프롬프트
    audio/001_*.wav …         줄별 나레이션
    narration.wav             이어붙인 나레이션
    clips/scene_01.mp4 …      TopView 결과물
    subs.ass
    out/final.mp4
```

## 절대 규칙

1. **길이를 먼저 정하지 않는다.** 대본 → 나레이션 실측 → 길이 확정 순서를 지킨다
2. **컨펌 지점을 건너뛰지 않는다.** 0·2·6·8단계. 되돌리는 비용이 가장 큰 지점들이다
3. **스타일 포뮬러는 한 글자도 바꾸지 않는다.** 문구를 다듬는 순간 컷 사이 룩이 흔들린다
4. **나레이션은 반드시 줄별로 합성해 실측한다.** 통짜 합성 금지. 줄별 시각이 자막 정렬의 근거다
5. **화면에 생성 글자를 넣지 않는다.** 생성 모델의 글자 렌더링은 영어라도 신뢰할 수 없다.
   정보는 주황색 선·화살표·링으로 표현하고 말은 나레이션이 담당한다.
   자막은 ffmpeg가 굽는 `subs.ass`로만 넣는다
6. **사람을 넣지 않는다.** 모든 프롬프트 네거티브에 `people, figures, hands`를 유지한다.
   하중은 사람 대신 돌덩이나 화살표로 표현한다
7. **통념은 영어권 기준으로 잡고 웹 검색으로 확인한다.** 번역으로 때우지 않는다
8. **근거 출처를 `script.json`에 남긴다.** 이건 형식이 아니라 채널의 생존 조건이다.
   유튜브의 비진정성 콘텐츠 정책은 "창작자의 독창적 통찰 없이 템플릿으로 대량생산한 인상을 주는
   AI 콘텐츠"를 채널 단위로 잡아낸다. 통념을 뒤집는 각도와 그 근거가 이 채널의 방어선이다
9. **크레딧이 부족하면 영상 블록 생성 전에 알린다.** 이미지보다 영상이 훨씬 비싸다

## 판단이 필요할 때

- **원리가 복잡할 때** → 영상을 늘려도 되지만 먼저 설명 범위를 좁혀 본다. "어떻게 서 있는가" 하나만 다루는 편이 대개 낫다
- **대본이 아주 짧을 때** → 그대로 짧게 만든다. 블록 수를 줄이고(2블록, 심지어 1블록) 실측 길이에 맞춘다
- **한 컷이 3초 넘게 정지해 보일 때** → 슬라이드쇼로 읽힌다. 해당 블록을 컷 시각을 명시해 재생성한다
- **엔진이나 보이스를 바꿀 때** → 발화 속도가 다르다. 반드시 다시 실측한다
- **주제가 영어권에 안 알려진 구조물일 때** → 통념이 없으면 훅도 없다. 주제를 바꾸거나,
  "이런 게 있다"가 아니라 "네가 아는 저것과 같은 원리다"로 각도를 튼다
- **TopView MCP가 안전 검사기 오류로 반려될 때** → 도구 문제가 아니라 권한 모드 문제다.
  권한을 도구 허용 쪽으로 바꾸면 풀린다. 프롬프트를 `prompts.json`에 남겨 두면 사용자가 직접 돌릴 수도 있다

## 톤

나레이션은 사실 중심의 담백한 설명체다. 현재형 평서문으로 간다.

쓰지 않는다: `Hey guys`, `Did you know`, `You won't believe`, `Let's dive in`,
`Amazing`, `Incredible`, 느낌표.

첫 문장은 짧고 단정적으로 시작해 시청자를 붙잡고, 마지막 문장은 앞의 훅을 다시 뒤집어 마무리한다.
한 문장에 정보는 하나만 담는다. 관계대명사로 문장을 늘리지 않는다.

```
That spire was not built to stop lightning.     ← 짧고 단정적
It was built to dock airships.                  ← 한 문장에 하나
```

사용자가 직접 쓴 대사는 이 톤 규칙보다 우선한다.

## 수익 구조에 대한 메모

쇼츠 RPM은 롱폼의 3~14%다. 이 스킬이 만드는 쇼츠는 **유입 장치**지 수익원이 아니다.
같은 대본·같은 에셋으로 8~20분 롱폼을 붙일 때 영어권 교육 분야의 높은 단가가 의미를 갖는다.
사용자가 수익을 물으면 이 구조를 먼저 말한다.
